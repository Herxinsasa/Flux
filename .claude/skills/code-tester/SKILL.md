# Code Tester - 测试验证

## 定位

`code-tester` 负责验证代码是否满足需求项、开发计划和界面契约。

它不直接修 Bug。发现失败时先收集证据、形成最小复现，再分类回退。修复由 `bug-fixer` 或前置流程完成。

---

## 铁律

**不复现就不修复。** 测试失败必须先记录失败命令、输入、日志、截图或操作步骤，并确认当前代码能稳定复现，再进入修复流程。

---

## 输入

| 输入 | 用途 |
|------|------|
| 开发计划 | 确认任务、状态、验收标准和测试范围 |
| 需求设计文档 | 确认需求项、契约设计、验证计划和编码上下文 |
| 界面设计文档 | 涉及 UI 时确认界面契约、状态、交互和 UI 验收方式 |
| code-review 结果 | 确认审查结论、接受风险和需重点测试的风险点 |
| dev-builder 执行记录 | 确认修改文件、验证记录和已知限制 |
| 代码变更文件 | 确定测试影响面和回归范围 |

---

## 测试深度

基础测试深度由需求项级别决定，并受聚合风险、UI 影响、回归风险调整。

| 级别 | 默认深度 |
|------|---------|
| 微 / XS | 编译或静态检查 + 核心路径手工验证 |
| 小 / S | 局部测试 + 关键异常场景 |
| 中 / M | 验收场景 + 受影响模块回归 |
| 大 / L | 端到端测试 + 跨模块回归 + 兼容/升级验证 |

加深规则：

- 有聚合风险：增加组合测试和任务间联调。
- 涉及 UI：增加界面契约测试，覆盖默认、加载、空、错误、禁用、成功状态中与本需求相关的状态。
- code-review 标记回归风险：增加受影响模块回归。
- 涉及数据迁移或兼容：增加旧数据、默认值、回退验证。
- 需求设计包含线程、并发、缓存或资源生命周期约束：增加对应竞态、一致性、失效、释放或取消场景验证。

## 工作流程

### Step 1：确定测试范围

从开发计划和 code-review 结果提取：

- 已完成任务。
- 关联需求项。
- 修改文件。
- 验收标准。
- UI 契约。
- code-review 接受风险和回归风险。
- 开发计划中的 `VERIFY-xxx` 验证清单。

### Step 2：执行测试

按测试深度执行：

| 类型 | 内容 |
|------|------|
| 编译/构建 | xmake、cmake、npm、cargo、go、dotnet、python 语法检查等 |
| 单元/局部测试 | 输入输出、边界值、异常路径 |
| 集成测试 | 接口调用、数据流、模块联动 |
| UI 验证 | 页面/窗口、字段、交互、状态、视觉约束 |
| 回归测试 | 受影响旧功能、兼容、配置、数据 |
| 运行时约束验证 | 线程切换、并发一致性、缓存更新/失效、资源释放和性能边界 |

每个场景记录：测试命令或步骤、输入、结果、证据。

执行后同步更新开发计划中对应 `VERIFY-xxx` 的状态和结果。需要新增或修改自动化测试代码时，不由 `code-tester` 直接编辑；将其路由为 `dev-builder` 的编码任务，再回到本 Skill 执行。

### Step 3：失败时建立最小复现

失败后先记录：

```text
□ 失败命令或操作步骤
□ 错误日志、堆栈、截图或返回值
□ 输入数据或配置
□ 当前分支和相关改动文件
□ 是否稳定复现
```

不能稳定复现时，标记为“待复现”，不要进入修复。

### Step 4：根因分类与路由

| 根因类型 | 定义 | 路由 |
|---------|------|------|
| 编码失误 | 需求和设计明确，实现写错 | `bug-fixer` |
| 编译失败 | 构建、类型、链接、依赖、语法错误 | `bug-fixer` |
| 边界遗漏 | 正常路径通过，极端输入、并发、异常状态失败 | `bug-fixer` |
| UI 契约遗漏 | 界面设计文档未覆盖必要状态或交互 | `ui-designer` |
| 设计遗漏 | 需求设计文档未覆盖接口、数据、错误处理或兼容策略 | `design-writer` |
| 影响面遗漏 | 测试发现影响范围超出原分析 | `impact-analyzer` |
| 需求遗漏 | 验收标准没有覆盖真实业务场景 | `spec-analyzer` |

### Step 5：复测闭环

`bug-fixer` 修复后回到 `code-tester` 复测：

- 原最小复现必须通过。
- 原验收场景必须通过。
- 修复涉及的影响面必须回归。

复测通过后，输出测试通过结论。复测失败则带证据回到 `bug-fixer`。

## 自审查

```text
□ 是否基于开发计划和需求项确定测试范围？
□ 涉及 UI 时是否测试界面契约？
□ 是否根据聚合风险、UI 影响、回归风险调整测试深度？
□ 失败时是否有最小复现和证据？
□ 编译失败是否路由到 bug-fixer？
□ 是否没有直接猜测性修复？
```
