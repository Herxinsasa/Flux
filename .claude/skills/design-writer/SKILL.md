# Design Writer - 详细设计

## 定位

基于需求分析与影响面分析结果，生成 AI-native 的需求设计文档。核心目标：**把编码需要知道的事实、契约、边界、任务和验证方式写清楚，降低 AI 编码偏离、遗漏和过度开发的概率。**

不覆盖“跳过详细设计”的微需求项。微需求项由 `impact-analyzer` 输出实现要点，后续由 `dev-builder` 临时组装编码输入。

---

## 设计原则

1. **有据可依。** 每个关键结论绑定影响面分析证据、图谱复核结果、代码探查结果或用户确认。
2. **先验事实优先。** 设计前必须读取 `spec-analyzer` 与 `impact-analyzer` 输出；涉及代码契约时必须用 GitNexus / codegraph / grep / glob 复核关键事实。
3. **按需求项设计，按需求输入成文。** 一次需求输入生成一个需求设计文档，文档内包含一个或多个需求项的详细设计，并记录需求项依赖。
4. **不过度设计。** 只写本次变更需要约束编码的内容，无关章节直接省略，不为模板完整而扩写。
5. **契约写死。** 接口签名、数据类型、默认值、兼容策略、错误处理、UI 交互和验证标准必须具体；不能写“参考现有方式”这类不可执行描述。
6. **低置信度不进计划。** 置信度为“低”的推断进入未决问题，不进入实现分解建议或编码上下文。
7. **运行时风险显式化。** 线程、并发、缓存、资源生命周期或性能影响一旦存在，就属于设计约束，不能留给编码阶段临时决定；不涉及的维度不展开。
8. **一份设计闭合实现。** 前端/客户端与后端/服务端技术设计放在同一份需求设计中，按实际影响保留章节，不能拆成互不闭合的实现文档。

---

## 输入

- `spec-analyzer` 输出：需求输入、迭代需求文档、需求项、业务规则、异常场景、验收标准、UI 影响、需求项依赖关系。
- `impact-analyzer` 输出：需求项级别、影响模块、影响明细、接口变更、数据变更、聚合风险、是否进入详细设计、是否需要 `ui-designer`。
- 图谱/代码探查结果：GitNexus / codegraph / grep / glob 得到的模块职责、接口签名、调用链、数据结构、测试入口。
- `ui-designer` 输出：仅当需求项涉及 UI 时读取，作为界面契约来源。

## 模板文件

| 模板 | 用途 | 维护规则 |
|------|------|---------|
| `references/需求设计_模板.md` | 单次需求输入的需求设计文档 | 每次进入详细设计时生成或更新 |
| `references/模块设计_模板.md` | 模块长期事实 | 仅当稳定模块职责、稳定接口、核心数据结构发生变化时回写 |
| `references/软件架构_模板.md` | 架构总览参考 | 仅当架构事实变化时回写 `docs/overview/architecture.md` |

需求设计文档服务于当前迭代编码；模块设计和架构总览服务于长期知识沉淀。不要把一次性需求细节回写到长期文档。

## 工作流程

### Step 1: 读取输入

确认已获取：

- 需求项及其级别。
- 需求项依赖关系。
- 影响面分析证据。
- 是否存在 UI 影响。
- 是否存在聚合风险。
- 影响面状态是否为“已闭合”，编码相关阻塞问题是否为 0。

缺失关键输入、影响链路未闭合或存在编码相关未决项时停止，不直接编写设计。

### Step 2: 图谱复核

对进入详细设计的需求项做最小必要复核：

| 复核对象 | 复核内容 |
|------|------|
| 模块职责 | 需求项是否落在正确模块，是否存在跨模块职责漂移 |
| 接口签名 | 函数、REST、RPC、事件、消息或其他真实通信接口的名称、参数、返回、异常是否存在或需要新增 |
| 数据结构 | 表、字段、配置项、枚举、DTO、缓存结构是否真实存在或需要新增 |
| 调用链 | 从入口、请求构造、通信边界、接收处理到返回展示是否闭合 |
| 运行时约束 | 是否涉及线程归属、并发同步、缓存一致性、资源生命周期或性能边界 |
| UI 入口 | 涉及 UI 时，页面、组件、状态、交互入口是否明确 |
| 测试入口 | 可验证位置、现有测试文件或手工验证入口是否明确 |

复核失败或证据不足时，写入“未决问题”并停止流转，不要把推断写进实现分解。修改跨层契约时应精确到真实类名、函数签名、字段和路径；内部辅助实现只需给出关键编码锚点，不要求穷举所有函数。

### Step 3: 写需求设计文档

使用 `references/需求设计_模板.md`。一次需求输入生成一个文档，文档内按需求项展开。

文件命名：

```text
docs/design/<需求迭代编号>-<需求主题>-req-design.md
```

示例：

```text
docs/design/v2.6.0-tire-guide-req-design.md
```

填写深度：

| 需求项级别 | 填写要求 |
|------|------|
| 小 / S | 写清设计范围、当前事实、契约设计、实现要点、编码上下文 |
| 中 / M | 在小需求项基础上补充设计决策、影响面、运行时约束、验证计划、风险 |
| 大 / L | 在中需求项基础上补充跨需求项依赖、升级/回退、模块/架构回写计划 |

微 / XS 原则上不进入详细设计；如果聚合风险或用户要求导致进入详细设计，按小 / S 处理。

### Step 4: 处理 UI 影响

需求项涉及 UI 时，必须读取 `ui-designer` 输出，并在需求设计文档中写入“界面契约引用”。

`design-writer` 不替代 UI 设计。`docs/ui` 只提供界面稿、界面契约和验收依据；目标源码、组件/类拆分、状态管理、数据映射和兼容策略由本需求设计统一说明。

需求涉及跨层实现时，在同一需求项内按实际影响写清：

- 界面契约引用。
- 客户端/前端技术设计。
- 服务端/后端技术设计。
- 跨层数据与接口契约。
- 端到端关键流程。

### Step 5: 处理跨端接口契约（仅分离开发）

需求涉及前后端分离、由不同人/团队负责、且存在跨端通信契约（接口签名、结构体、错误码）时，先自推断是否需要独立的接口契约文档，再向用户确认。

判定为“分离开发”的信号：

| 信号 | 说明 |
|------|------|
| 前后端两端实现 | 需求同时涉及前端/客户端与后端/服务端 |
| 不同人/团队负责 | 前后端由不同开发者并行开发 |
| 跨端通信契约 | 存在 HTTP/RPC/消息/共享结构体等双方共同约定 |

非分离开发（单端、同一人负责全栈、无跨端契约约定）时，不单独产出接口契约文档，契约写在需求设计正文的“跨层数据与接口契约”即可。

确认流程：

```text
自推断是否“分离开发 + 跨端契约”
  → 向用户说明推断依据，确认是否产出接口契约文档
    ├─ 用户确认不写（非分离）→ 契约留需求设计正文 → 进入设计确认
    └─ 用户确认写（分离）→ 产出轻量接口契约文档 → 契约确认门 → 通过后进入设计确认
```

接口契约文档命名：

```text
docs/protocol/<需求迭代编号>-<需求主题>-contract.md
```

接口契约文档只写边界、不写内部实现，内容保持轻量：

- 维护方与消费方（一般为后端维护、前端消费）。
- 接口签名（函数、REST、RPC、事件或消息）。
- 数据结构体（字段、类型、约束、默认值）。
- 错误码定义。
- 变更同步约定（由维护方同步消费方）。

接口契约文档不单独建模板、不引入版本号。

契约确认门：接口契约由维护方（后端）定义，消费方（前端）确认对齐后，方可进入 `dev-planner`。契约未确认前不得生成开发计划。

### Step 6: 图表使用

图表不是必填项。AI 编码更依赖精确契约、文件边界和验证标准。

仅在以下情况使用 Mermaid：

- 调用链或异步流程用文字/表格难以说明。
- 跨模块依赖需要防止编码改错方向。
- 状态机、线程、数据流是本次变更风险点。

优先使用表格；需要画图时只画本次变更路径，不引入完整图表规范。

### Step 7: 设计确认

以下情况在进入 `dev-planner` 前必须由用户确认需求设计：

- 中 / M、大 / L 需求项。
- 小 / S 需求项涉及接口兼容、数据迁移、线程并发、缓存一致性、关键 UI 交互或不可逆变更。
- 存在会影响实现方向、范围或验收方式的未决问题。
- 分离开发场景产出的接口契约文档，须通过契约确认门确认。

不满足以上条件且没有阻塞问题的小 / S 需求项，可标记“无需单独确认”后继续。设计待确认或存在任何影响编码的 TBD 时停止流程，不得生成可执行开发计划。与本次实现无关的问题移入“非本次范围”；设计阶段不得自行拍板需求未确认事项。

### Step 8: 自审查

提交需求设计文档前检查：

```text
□ 是否存在已废弃术语残留？
□ 是否一个需求输入只生成一个需求设计文档？
□ 每个进入详细设计的需求项是否有图谱复核摘要？
□ 接口、数据、UI、错误处理、兼容策略是否具体？
□ 涉及线程、并发、缓存、资源生命周期或性能时，是否形成可执行约束？
□ 低置信度推断是否进入未决问题，而不是实现分解建议？
□ 编码上下文是否明确允许修改、禁止修改和验收标准？
□ 涉及 UI 的需求项是否引用 ui-designer 的界面契约？
□ 需求项依赖是否已记录？聚合风险是否只用于提示整体交付风险，而不是改写单个需求项级别？
□ 需要用户确认的设计是否已确认？
□ 分离开发场景是否产出接口契约文档并通过契约确认门？非分离场景契约是否写在需求设计正文？
```

## 增量更新

同一份需求输入反复补充时，更新同一个需求设计文档：

- 新增或修改内容直接更新到对应章节。
- 重要变更写入“修订记录”。
- 删除或废弃的设计从正文移除，并在修订记录中说明。

不要使用高亮标记包裹长期保留内容，避免文档噪声影响 AI 编码。

---

## 回写机制

需求设计完成后，如果产生长期事实，再按三层文档维护：

- 模块职责、稳定接口、稳定数据结构变化：默认回写 `docs/modules/<module-name>/README.md`；多工程仓库可回写 `projects/<project>/docs/modules/<module-name>/README.md`。
- 模块文档不存在时：先参考现有 `docs` 下的模块资料；仍不存在则基于 GitNexus / codegraph / grep / glob 的证据创建模块描述骨架，只写已确认事实，未知内容写“待确认”。
- 架构边界、部署关系、跨系统协议变化：回写 `docs/overview/architecture.md`。如果当前仓库缺少该文件，仅在架构事实确实变化时创建。
- 一次性实现步骤、临时方案、当前需求验收细节：只保留在需求设计文档中。
