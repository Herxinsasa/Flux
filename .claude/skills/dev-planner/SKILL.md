# Dev Planner - 开发计划

## 定位

把已确认的输入整理成可执行、可恢复、可审查的开发计划。正式 `TASK-xxx` 只在开发计划中存在。

本 Skill 不重新拆需求、不补设计决策、不把联调或回归执行伪装成编码任务。

## 进入门禁

以下条件必须同时满足：

```text
需求规格 = 已确认
需求阻塞问题 = 0
影响面 = 已闭合
影响面编码阻塞问题 = 0
需求设计 = 已确认或无需单独确认（需要设计时）
需求设计编码相关 TBD = 0
界面契约 = 已确认（涉及 UI 时）
```

任一条件不满足时只记录阻塞项，不生成可执行任务，不以计划内容替代缺失决策。

## 输入

| 输入 | 用途 |
|------|------|
| `docs/requirements/...-req.md` | 已确认范围和验收标准 |
| `docs/requirements/...-impact.md` | 闭合链路、关键路径、聚合风险、跳过详设的实现要点 |
| `docs/design/...-req-design.md` | 前后端统一技术设计、契约、编码边界、实现分解建议 |
| `docs/ui/...-ui.md` | UI 稿、界面契约和 UI 验收依据 |
| 代码基线 | 区分当前迭代和用户已有改动 |

没有 UI 影响时不读取界面设计文档。跳过详细设计的需求项从影响面实现要点生成任务。

## 核心规则

1. 每个任务绑定需求项、目标路径/对象、输入契约、允许/禁止范围和验收标准。
2. 依赖优先、契约优先，高风险技术探针优先。
3. 同文件、同接口、同配置或同 UI 区域的任务显式标注冲突并串行。
4. 生产代码和自动化测试代码属于编码任务；执行编译、联调、端到端和回归属于验证清单。
5. 每个编码任务结束时应保持代码可编译或形成明确阻塞，不安排长期破坏构建的“只改头文件”任务。
6. 不把低置信度或待确认内容写入任务。
7. 记录基线提交和迭代开始时已有变更，不自动纳入用户原有修改。

## 工作流程

### Step 1：记录基线并检查输入

```powershell
git rev-parse HEAD
git status --short
```

记录 `baseline_commit` 和 `pre_existing_changes`。基线变化或输入文档状态失效时，先回到影响面检查。

### Step 2：生成编码任务

任务类型只包含实际代码或必要技术产物：

- 前置技术验证。
- 公共契约/数据结构/配置。
- 转换、序列化和数据映射。
- 核心业务/服务端实现。
- 客户端适配、通信和状态。
- UI 实现。
- 自动化测试代码。
- 必要文档回写和提交准备。

类型化/C++ 项目按实际依赖优先考虑：

```text
公共枚举/结构/schema/proto/公开契约
  -> 序列化与映射
  -> 核心/服务端实现
  -> 客户端适配与通信
  -> 前端状态与 UI
  -> 自动化测试代码
```

这不是机械的“全部头文件先改”，而是保证被依赖契约先稳定，并在同一任务内补齐维持可编译所需的最小实现。

### Step 3：生成验证清单

将不修改生产代码的执行活动列为 `VERIFY-xxx`，由 `code-tester` 使用：

- 编译/构建与静态检查。
- 单元/集成测试执行。
- 前后端或跨模块联调。
- 端到端验收。
- 回归、兼容、升级/回退和 UI 验收。

验证清单不进入 `dev-builder` 的编码任务队列。验证失败按 `code-tester` 规则路由；修复代码时再创建或恢复编码任务。

### Step 4：分析依赖、冲突和状态

`TASK-xxx` 初始状态为“待执行”或“阻塞”。状态枚举：

```text
待执行 / 执行中 / 已完成 / 阻塞 / 跳过
```

明确任务依赖、文件冲突和可并行关系。无法确认的依赖进入阻塞项。

## 自审查

```text
□ 所有进入门禁是否满足？
□ 正式 TASK 是否只存在于开发计划？
□ 前端技术任务是否来自同一份需求设计，UI 约束是否来自界面设计？
□ 跨层字段是否包含转换、接收、持久化和返回相关任务？
□ 自动化测试代码与测试执行是否正确分开？
□ dev-builder 是否只会取得 TASK，不会取得 VERIFY？
□ 是否记录基线、已有变更、依赖、冲突和阻塞？
```
