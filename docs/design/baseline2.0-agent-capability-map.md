# Flux baseline2.0 文档 Agent 阶段 0：能力地图

## 结论

Flux 已具备文档 Agent 的核心执行底座，不需要从零建设 Agent Runtime。当前形态是“对话驱动的工具 Agent”：可组装文档上下文、调用内置工具、注入 Skill 与批注、流式展示过程，并以预览加确认的方式写回文件。

下一阶段的重点不是增加更多工具，而是将现有能力收敛为可解释、可约束、可验证的文档任务流程。

## 当前执行链路

```text
ChatPanel
  -> 组装当前文件、选区、引用、附件、历史、会话摘要与固定结论
  -> agent.send IPC
  -> Agent handlers：系统规则 + Skill 匹配 + 上下文预算 + 可写目录
  -> AgentProcessManager：取消、5 分钟超时、最多 3 次重试
  -> runAgent：模型调用 <-> 工具调用，最多 10 轮
  -> Stream events：正文、推理、工具调用、工具结果、进度
  -> ChatStore / ToolCallCard
  -> write_file：生成预览 -> 用户确认 -> editor.applyChange 写入
```

## 能力矩阵

| 能力 | 当前实现 | 已有保护 | 阶段 0 判定 |
|---|---|---|---|
| 当前文档上下文 | 默认仅注入当前预览文件；可附带选区、引用与附件 | 单文件注入上限 24,000 字符；大于 512KB 仅注入元信息或日志索引摘要 | 可用 |
| 对话历史 | 最近最多 24 条、约 140,000 字符；仅最近两条助手消息保留推理内容 | 长对话自动压缩、95% 输入占用时阻止发送 | 可用 |
| 批注上下文 | 用户问题或 Skill 名匹配“批注/评审”等意图时，注入当前文件未关闭批注 | 最多 20 条、6,000 字符；不注入 `.review.json` 本身 | 可用，但触发规则隐式 |
| Skill | 支持 `/skill` 显式调用、关键词自动匹配、工作区本地 Skill | 失效 Skill 跳过；正文仅注入系统提示 | 可用，但不是独立执行步骤 |
| 读取文件 | `read_file` 分段读行 | 默认 2,000 行、最大 5,000 行；结果裁剪 | 可用，但读取范围未限制在工作区 |
| 搜索内容 | `search_content` 使用正则递归搜索 | 跳过二进制、`node_modules`、`.git`；最多 2,000 行结果 | 可用，但搜索目录由模型决定，缺少范围约束 |
| 文件信息 | `get_file_info` 读取大小、行数、编码、扩展名 | 无显式目录范围限制 | 可用，但应与只读授权统一 |
| 网页读取 | `fetch_webpage` 获取 HTTP/HTTPS 页面后抽取文本 | 12 秒默认超时、结果裁剪 | 可用；后续需明确网络访问策略 |
| 文件修改 | `write_file` 只生成修改计划，不直接落盘 | 写入路径限制；预览、撤销、确认；覆盖未保存文件前二次确认 | 可用，安全模型正确 |
| 批量修改 | 多个 `write_file` 可用 `transactionId` 分组 | 现有预览与事务应用入口 | 可用，任务级状态尚未展示 |
| 过程展示 | 流式正文、推理、工具卡片、工具进度、失败信息 | 工具输出在 UI 与模型历史中裁剪 | 可用，但缺统一任务时间线 |
| 会话恢复 | JSONL 事件 + checkpoint + pinned facts + 工作摘要 | 原子写入、检查点回退、清理策略 | 默认关闭；开启后会保存普通会话，不仅是任务摘要 |

## 数据与权限边界

### 已满足的边界

- `write_file` 不直接修改文件，只返回修改预览。
- 确认写入前会检查目标文档是否有未保存内容。
- 写入路径限定为工作区、已打开文件或附件所在目录、用户数据目录和用户 Skill 目录。
- 大日志不注入全文，优先提供索引摘要并引导 Agent 再搜索、分段读取。

### 需要在后续收敛的边界

- `read_file`、`get_file_info` 和 `search_content` 未与工作区或用户显式附加文件绑定；模型传入任意本地绝对路径即可尝试读取或搜索。
- `fetch_webpage` 允许任意 HTTP/HTTPS 地址；尚未定义内网、重定向和敏感地址的访问策略。
- Agent 失败后会重试整个运行；读取和网页抓取可能重复执行，尚无任务级幂等记录。

## 当前可观察性

用户目前可以看到工具名称、工具参数摘要、执行结果、修改 diff、进度文本和错误信息。系统也会记录上下文裁剪、Skill 注入、运行状态和工具结果。

尚未具备：

- 一个可折叠的任务卡，统一呈现目标、计划、工具序列、文件影响和最终状态。
- 结构化的“结论引用了哪些文档/行号/批注”证据清单。
- 用户可见的 Skill 推荐原因与自动匹配说明。
- 任务级取消、重试、恢复和已确认修改的完整审计视图。

## 关键设计判断

### Flux 不是通用自主 Agent

Flux 的合理定位是“当前工作区的文档任务 Agent”。它应优先解决阅读、评审、根据批注修改、总结和结构化改写，而不是开放终端、自动部署或多 Agent 编排。

### 先收紧读取，再扩展能力

已有写入确认机制是正确的，但读取与搜索范围还不够明确。阶段 1 应先将只读工具统一为“当前工作区 + 用户显式引用/附件”的授权模型，再增加任务卡或新工具。

### 会话策略需要维持轻量

当前会话持久化默认关闭，这符合 Flux 的轻量编辑器定位。阶段 5 不应默认保存完整普通聊天，而应优先保存未完成任务的摘要、来源文件和确认过的变更记录。

## 阶段 1 输入：文档只读工具集

### 最小目标

让 Agent 能在授权范围内可靠完成“读取当前 Markdown 与关联批注，生成带依据的评审结论”，不修改任何文件。

### 需要定义的契约

| 项目 | 目标规则 |
|---|---|
| 读取授权 | 当前工作区根目录、当前文件、用户显式 `@` 附件；其他路径拒绝并说明原因 |
| 搜索授权 | 仅允许已授权根目录；搜索结果需带文件与行号 |
| 上下文来源 | 当前文件、选区、显式引用、批注分层注入，并在 UI 显示来源 |
| 工具结果 | 统一返回结构化元数据：来源路径、行号范围、截断状态、读取原因 |
| 首个任务 | “审阅当前文档未关闭批注，并列出需修改项及对应引用”；不调用 `write_file` |

### 阶段 1 明确不做

- 新增写入工具或改变现有确认写入流程。
- 自动调用 Skill；仅保留现有显式调用与自动注入行为。
- 任务恢复、多 Agent、终端工具或跨工作区搜索。
