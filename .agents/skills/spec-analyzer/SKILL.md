# Spec Analyzer - 需求分析

## 定位

`spec-analyzer` 是 DevFlow 的入口 Skill，只回答“要做什么”。它负责把需求输入整理成结构化、低噪声、可确认的需求规格文档。

本 Skill 不做最终影响面分析、不写详细设计、不生成界面契约、不排开发计划、不编码。

---

## 角色要求

以严谨认真的开发精英标准处理需求：少废话、重边界、重确认。用户可以表达得粗糙，但输出必须清楚、可验收、可交给后续流程。

---

## 核心原则

1. **不确定就确认。** 默认值、异常路径、UI 行为、兼容策略、接口含义、数据口径不明确时，必须向用户确认，不允许自己假设后继续。
2. **言简意赅。** 需求规格只保留后续设计和编码需要的信息，避免长段背景叙述和重复解释。
3. **按需求项组织。** 需求项是最小分析、设计、开发、验收单位。
4. **级别只显示中文。** 需求项中只写“微 / 小 / 中 / 大”，不同时展示内部枚举。
5. **确认后才流转。** 需求规格文档生成后必须让用户确认；未确认不得自动进入影响面分析。
6. **语义关系按需确认。** 新对象与现有对象存在继承、扩展、替代或差异关系时，必须明确一致行为和差异行为；普通需求不增加该分析。

---

## 输入

- 用户的需求描述、需求文档、Issue、截图说明或口头需求。
- 用户提供的 UI 稿、截图、Figma、Pencil、HTML 原型。
- 已有需求文档或历史迭代文档。

---

## 输出

使用模板：

```text
references/需求规格_模板.md
```

写入路径：

```text
docs/requirements/<需求迭代编号>-<需求主题>-req.md
```

示例：

```text
docs/requirements/v2.6.0-tire-guide-req.md
```

## 工作流程

### Step 1：提取需求项

从需求输入中拆分需求项。拆分原则：

- 一个独立业务动作、界面动作、接口能力、数据变更或兼容点，通常是一个需求项。
- 耦合需求项拆开分析，在“需求项依赖”中记录关系。
- 不同页面、接口、数据对象或验收标准不同，不合并。

### Step 2：补齐最小必要信息

每个需求项必须包含：

```text
□ 需求项ID
□ 需求项名称
□ 级别：微 / 小 / 中 / 大
□ 目标
□ 触发条件
□ 正常路径
□ 验收标准
□ UI 影响：是 / 否
□ 待确认问题：无 / 有
```

可选但必要时填写：

```text
□ 异常场景
□ 依赖需求项
□ 兼容要求
□ 非目标
□ 初步影响范围
```

### Step 3：识别语义关系

当需求引入新的类型、模式、状态、枚举值或规则标识，并可能复用或改变现有对象行为时，记录：

```text
□ 关系：独立 / 继承 / 扩展 / 替代
□ 参考对象
□ 一致行为
□ 差异行为
```

语义关系影响需求范围或验收标准但尚未确认时，作为阻塞级待确认问题。普通字段、文案和独立逻辑修改不生成该内容，也不因存在语义关系机械拆分需求项。

### Step 4：识别 UI 影响

涉及以下任一内容，标记 `UI影响：是`：

- 页面、窗口、表单、弹窗、菜单、按钮。
- 文案、提示、错误消息、空状态、加载状态。
- 字段显示、字段编辑、默认值、单位、校验提示。
- 交互路径、显示隐藏、启用禁用、跨界面联动。
- 用户提供了 UI 稿、截图、Figma、Pencil、HTML 原型。

本 Skill 只识别 UI 影响，不生成界面契约。界面契约由 `ui-designer` 输出。

### Step 5：记录依赖和聚合风险

记录需求项之间的依赖关系，以及多个需求项共同交付带来的整体风险。

聚合风险不改变单个需求项级别，只提示后续影响面分析、开发计划、测试和审查需要加深。

### Step 6：集中确认

把所有待确认问题集中列出，并向用户确认。

如果存在任何阻塞级待确认问题，或存在会影响方向、范围、验收、数据口径的未决项：

- 可以生成草稿文档。
- 文档状态必须标记为“待确认”。
- 不得触发 `impact-analyzer`。

### Step 7：用户确认关闸

输出确认摘要，让用户确认：

```text
需求项数量：
需求项级别：
UI 影响：
待确认问题：
是否确认进入影响面分析？
```

只有用户明确确认，且阻塞级待确认问题归零后，才将文档状态改为“已确认”，并允许进入 `impact-analyzer`。与本次实现无关的问题移入“非本次范围”，不要以 TBD 形式带入后续设计。

### Step 8：写入需求规格文档

按 `references/需求规格_模板.md` 写入 `docs/requirements/`。

---

## 自审查

输出前检查：

```text
□ 是否只显示中文级别？
□ 是否没有把 AI 假设写成事实？
□ 是否所有不确定项都进入待确认？
□ 是否未确认时阻止进入 impact-analyzer？
□ 是否没有写详细设计、接口契约或界面契约？
□ 存在语义关系时，是否明确参考对象、一致行为和差异行为？
□ 是否使用 docs/requirements 路径？
□ 是否言简意赅，没有无效背景和重复描述？
```
