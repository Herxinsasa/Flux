# Dev Builder - 编码调度

## 定位

`dev-builder` 是编码环节的调度者。它不重新拆需求、不重新做详细设计、不重新设计 UI。

它负责：

- 读取 `dev-planner` 输出的开发计划。
- 找到可执行任务。
- 为每个任务组装最小充分的编码输入。
- 使用独立 `implementer` sub-agent 执行任务，避免上下文污染。
- 对 implementer 结果做任务级需求对齐审查。
- 更新开发计划中的任务状态和执行记录。

---

## 核心原则

1. **每个任务独立 sub-agent。** 每个任务创建新的 implementer 实例，不继承上一个任务上下文。
2. **只给必要上下文。** 编码输入只包含当前任务需要的开发计划、需求设计、界面契约、编码规范和相关代码事实。
3. **编码前加载规范。** 先找规范再派任务；找不到规范时使用项目现有代码风格和本流程约束。
4. **状态可恢复。** 任务开始前标记“执行中”，完成后标记“已完成 / 阻塞 / 跳过”，并写入执行记录。
5. **手术式修改。** 只改任务要求范围内的文件和逻辑，不做无关重构、不引入额外抽象。
6. **任务级审查。** `dev-builder` 只做当前任务的需求对齐审查；整体代码质量终审交给后续 `code-review`。
7. **尊重代码基线。** 执行前核对开发计划中的基线提交和已有工作区变更，不覆盖、不改写、不自动归入用户原有修改。

---

## 输入

| 输入 | 用途 |
|------|------|
| 开发计划：`docs/plan/<需求迭代编号>-<需求主题>-dev-plan.md` | 读取任务、依赖、状态、验收标准 |
| 需求设计文档 | 读取需求项、编码上下文、实现分解建议和验证建议 |
| 界面设计文档 | UI 任务读取界面契约和 UI 验收依据；前端技术设计从需求设计读取 |
| `impact-analyzer` 输出 | 跳过详细设计的需求项、微需求项实现要点 |
| 编码规范和现有代码事实 | 约束实现风格、接口、错误处理和测试方式 |

---

## 工作流程

### Step 0：检查 implementer 可用性

编码前确认 Agent 工具能够发现并调用 `.claude/agents/implementer.md`。如果当前会话在复制或修改 Agent 文件前已经启动，应先重启 Claude Code 再检查。

如果 `implementer` 不可用：

- 返回 `BLOCKED_AGENT_UNAVAILABLE`。
- 不把 sub-agent 规则当作 inline 提示由主 Agent 直接编辑代码。
- 不将任务标记为“执行中”或“已完成”。
- 在开发计划阻塞项中记录环境原因。

### Step 1：加载编码规范

按优先级寻找并加载：

| 优先级 | 来源 | 内容 |
|--------|------|------|
| 1 | 项目根目录 `CLAUDE.md` | 项目级开发约束 |
| 2 | 仓库或模块编码规范 | 命名、错误处理、测试、日志、目录结构 |
| 3 | `.claude/constraints/` | 仓库级编码规范、接口规范、错误码规范 |
| 4 | `projects/<project>/docs/spec/` | 多工程差异明显时的工程级补充规范 |
| 5 | 协议、接口、数据文档 | 通信、数据、配置、兼容策略 |
| 6 | `.claude/constraints/coding-req.md`、`log-req.md` | DevFlow 自带编码与日志约束基线，项目无更高优先级规范时遵循 |
| 7 | 同模块现有代码 | 命名、缩进、注释、分层和测试风格 |

未找到显式规范时，不阻塞开发；使用现有代码风格和当前任务约束。编码与日志约束基线（`.claude/constraints/coding-req.md`、`log-req.md`）始终随编码输入注入，作为最低遵循标准。

编码前提取项目代码约定：从目标任务文件同目录或同模块读取 1~2 个代表性现有文件，确认——(a) 编码（字符集 + BOM）与行尾；(b) 代码风格（命名、缩进、大括号、注释格式、代码组织顺序、日志位置等）。提取到的项目约定优先于 `.claude/constraints/` 基线，仅当项目约定自相矛盾或明显错误时标记给用户；记录代表性样例文件路径。

### Step 2：读取开发计划

读取：

```text
docs/plan/<需求迭代编号>-<需求主题>-dev-plan.md
```

先核对当前 HEAD 与计划中的基线提交。HEAD 已变化时暂停执行并重新检查影响面和任务有效性；工作区存在计划记录之外的改动时保留原状，只处理能够证明属于当前任务的文件和代码区域。

选择第一个满足条件的任务：

- ID 为 `TASK-xxx`，不是 `VERIFY-xxx`。
- 状态为“待执行”。
- 依赖任务均为“已完成”，或计划中明确可用 mock 解耦。
- 不存在未解决的阻塞项。

如果没有可执行任务，输出原因：

- 所有任务已完成。
- 剩余任务被依赖阻塞。
- 剩余任务需要人工确认。
- 剩余内容仅为验证清单，应进入 `code-review` 和 `code-tester`。

### Step 3：更新任务为执行中

派发前先更新开发计划：

- 任务状态：`待执行` → `执行中`
- 执行记录：写入开始时间、任务 ID、状态变化说明

### Step 4：组装编码输入

编码输入不单独落盘，只作为 implementer 的任务上下文传入。

| 任务来源 | 编码输入 |
|---------|---------|
| 进入详细设计的需求项 | 开发计划任务项 + 需求设计文档相关章节 + 运行时约束 + 编码上下文 + 验收标准 + 编码规范 |
| 涉及 UI 的需求项 | 上述内容 + 界面设计文档的界面契约和验收依据 + 需求设计中的前端/客户端技术设计 |
| 跳过详细设计的需求项 | 开发计划任务项 + impact-analyzer 实现要点 + 影响面 + 验收标准 + 编码规范 |
| 微需求项 | 开发计划任务项 + 需求描述 + 验收标准 + 目标文件 + 编码规范 |

编码输入必须包含：

```text
□ 当前任务目标
□ 来源需求项
□ 允许修改范围
□ 禁止修改范围
□ 目标文件或对象
□ 验收标准
□ 相关接口、数据或 UI 契约
□ 相关线程、并发、缓存、资源生命周期或性能约束
□ 编码约束（`.claude/constraints/coding-req.md`、`log-req.md`）与项目编码规范，作为强制遵循项
□ 项目代码约定（编码（字符集 + BOM）与行尾、风格要点、代表性样例文件路径），作为强制遵循项
```

低置信度、未决问题、阻塞项不得作为实现指令传给 implementer。

### Step 5：派发独立 implementer

每个任务派发一个新的 implementer sub-agent。

派发内容必须强调：

- 只完成当前任务。
- 不处理计划外需求。
- 不扩大修改范围。
- 必须遵循 `.claude/constraints/` 编码与日志约束及项目编码规范。
- 遇到输入缺口返回 `NEEDS_CONTEXT` 或 `BLOCKED`。
- 完成后返回修改摘要、文件列表、验证结果、编码约束遵循情况和风险说明。
- 返回可追踪的 `agent_name=implementer` 和 `agent_id`；无法取得 ID 时记录工具返回的等价执行标识。

implementer 返回状态：

| 状态 | 处理 |
|------|------|
| DONE | 进入任务级需求对齐审查 |
| DONE_WITH_CONCERNS | 进入审查，并重点检查 concerns |
| NEEDS_CONTEXT | 标记阻塞，记录缺少的上下文 |
| BLOCKED | 标记阻塞，记录阻塞原因 |

### Step 6：任务级需求对齐审查

implementer 返回后，逐项检查：

```text
□ 开发计划验收标准是否逐条满足？
□ 需求设计文档的编码上下文是否遵守？
□ UI 任务是否符合界面契约？
□ 修改文件是否在允许范围内？
□ 是否修改了禁止修改的文件或逻辑？
□ 是否引入计划外功能、重构或抽象？
□ 是否遵循 `.claude/constraints/` 编码约束（命名、编码格式、错误处理、日志）与项目编码规范？编码（字符集 + BOM）与行尾和项目既有约定冲突时是否以项目为准？
□ 必要验证是否已执行或说明无法执行原因？
```

审查结果：

- 全部通过：任务状态改为“已完成”。
- 有可修复偏差：重新派发同一个任务的修复指令给新的 implementer。
- 缺少输入：任务状态改为“阻塞”。
- 用户明确不做：任务状态改为“跳过”，记录原因。

### Step 7：更新开发计划

每个任务结束后更新：

- 任务状态。
- 执行记录。
- 修改文件摘要。
- 验证结果。
- 阻塞原因或跳过原因。
- 实际执行的 `agent_name`、`agent_id` 和返回状态。

不要修改需求设计文档或界面设计文档，除非任务明确要求文档回写。

### Step 8：继续下一任务

重复 Step 2 到 Step 7，直到：

- 没有可执行任务。
- 用户要求暂停。
- 出现需要人工确认的阻塞项。

---

## 输出

每轮编码结束后输出：

- 已执行任务 ID 和任务名。
- implementer 返回状态。
- 修改文件摘要。
- 验证结果。
- 需求对齐审查结果。
- 开发计划状态更新情况。
- 当前剩余任务或阻塞项。

---

## 自审查

调度过程中检查：

```text
□ 是否每个任务都使用独立 implementer sub-agent？
□ implementer 不可用时是否阻止 inline 编码？
□ 执行记录是否包含 agent_name、agent_id 和返回状态？
□ 是否只给当前任务必要上下文？
□ 是否读取并遵守开发计划状态？
□ 是否把任务状态更新写回开发计划？
□ UI 任务是否传入界面契约？
□ 跳过详细设计和微需求项是否使用 impact-analyzer 实现要点？
□ 是否避免无关重构和计划外功能？
□ 编码前是否再次确认编码约束（`.claude/constraints/`）已注入 implementer？
□ 是否记录验证结果和阻塞原因？
```
