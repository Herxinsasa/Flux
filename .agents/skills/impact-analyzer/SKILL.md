# Impact Analyzer - 影响面分析

## 定位

验证需求项实际影响哪些模块、接口、数据、UI 和测试入口，重点防止跨层链路遗漏。本 Skill 不重新拆需求、不做详细设计、不编码。

## 进入条件

以下条件必须同时满足，否则停止并回到 `spec-analyzer` 或用户确认：

- 需求规格状态为“已确认”。
- 阻塞级待确认问题为 0。
- 不存在影响方向、范围、验收或数据口径的未决项。

## 核心规则

1. **端到端闭合。** 涉及数据或行为传递时，必须沿真实技术链路验证入口、转换、传输、处理、持久化和返回展示，不能只检查两端。
2. **技术中立。** 通信边界按项目事实识别，可以是 REST、RPC、WebSocket、消息、IPC、本地调用或其他机制，不预设框架。
3. **证据简洁。** 结论绑定完整路径、真实符号和证据来源；不在产物中保留完整查询日志。
4. **同名消歧。** 同名或近似模块必须记录完整路径、职责、真实符号和可修改性，不能凭文件名认定调用关系。
5. **未决即阻塞。** 必需链路缺层、关键对象无法定位或编码边界不确定时，状态为“阻塞”，不得流转到 UI、详细设计或计划。
6. **级别只能升不能降。** 实际范围更大时升级；更小时保留需求规格初判。
7. **聚合风险独立记录。** 聚合风险影响计划、审查和测试深度，不改写单个需求项级别。
8. **语义引用按需闭合。** 需求定义语义关系时，必须同时检查变更对象和参考对象的相关引用；仅搜索新增名称不能判定影响面已闭合。

## 证据来源

按可用性使用 GitNexus、codegraph、其他代码图谱或 `rg`/glob 静态扫描。图谱不可用时使用静态扫描，并标明证据限制；只有静态证据也不足时才按保守策略升级。

## 工作流程

### Step 1：提取验证目标

每个需求项只检查与本次变更有关的维度：

| 维度 | 必须确认的内容 |
|------|----------------|
| 入口 | 页面、命令、事件、定时任务、外部请求或数据源 |
| 客户端/前端 | 状态、表单、模型、请求构造、响应映射 |
| 通信边界 | 实际协议或适配层、序列化/反序列化或等价转换 |
| 服务端/接收端 | 接收入口、业务处理、校验、错误路径 |
| 数据 | 结构、默认值、持久化、缓存、兼容或迁移 |
| 返回与展示 | 返回映射、状态更新、展示或最终结果 |
| 运行时 | 线程、异步、并发、资源生命周期、性能热路径 |
| 测试 | 现有测试、构建、联调或回归入口 |

### Step 2：验证端到端链路

按项目真实架构验证：

```text
入口/数据源
  -> 前端或客户端状态
  -> 请求构造/适配
  -> 实际通信边界
  -> 接收端入口
  -> 业务处理
  -> 持久化/缓存（如涉及）
  -> 响应映射
  -> 展示或最终结果
```

不涉及的层可以省略，但必须说明原因。新增或修改字段时，至少确认：

- 发送与接收两侧的字段映射。
- 序列化、反序列化或等价转换位置。
- 类型、单位、默认值、校验和兼容策略。
- 持久化、读取、缓存更新与返回展示是否闭合。

任一必需层缺少证据，链路状态为“未闭合”。

### Step 3：闭合语义引用

需求规格包含“语义关系”时，以变更对象和参考对象为语义锚点，检查：

- 直接引用和相关条件判断。
- `switch` 分支、映射转换和状态处理。
- 与一致行为或差异行为有关的实现位置。

有效引用归类为“需要修改”“无需修改”或“待确认”。同类且结论一致的引用可以合并；不记录搜索命令、完整查询过程和明显无关的文本命中。存在未归类或待确认引用时，影响面状态为“阻塞”。

### Step 4：消除同名对象歧义

发现同名文件、类或模块时，使用以下最小记录：

| 完整路径 | 真实符号 | 职责 | 可修改 | 与本需求关系 |
|----------|----------|------|---------|--------------|

特别区分源码代理/适配层、服务端实现、生成代码、二进制库和不可修改依赖。

### Step 5：确认级别和流程深度

发现未预期的接口、数据、通信、跨工程、不可回滚或多模块变更时升级需求项级别。

满足以下条件才允许跳过详细设计：

- 接口、数据结构、协议、配置结构、行为分支、兼容策略和运行时边界均不变。
- 端到端链路已闭合，修改位置和验收方式明确。
- 无编码相关未决项。

纯 UI 显示或过滤只有在数据已存在、规则已确认、修改局限于本地组件，且不影响跨层链路、共享状态、权限、协议、持久化和兼容时，才允许跳过详细设计。

跳过详细设计时必须给出可直接用于计划的实现要点：目标文件/符号、允许范围、禁止范围和验收标准。

### Step 6：判定 UI 影响

涉及页面、窗口、组件、字段、布局、交互、视觉或 UI 状态时触发 `ui-designer`。UI 稿和代码事实冲突时记录阻塞问题，不自行取舍。

### Step 7：输出影响面文档

写入：

```text
docs/requirements/<需求迭代编号>-<需求主题>-impact.md
```

建议结构：

```markdown
# <需求迭代编号>-<需求主题>影响面

> 状态：已闭合 / 阻塞
> 需求规格：<路径>
> 证据方式：GitNexus / codegraph / rg / glob

## 1. 结论

| 需求项 | 确认级别 | 链路状态 | UI | 详细设计 | 关键原因 |
|--------|----------|----------|----|----------|----------|

## 2. 端到端链路

| 顺序 | 层/边界 | 完整路径与符号 | 数据/行为变化 | 证据 |
|------|---------|----------------|---------------|------|

## 3. 影响明细

| 需求项 | 类型 | 完整路径/真实符号 | 操作 | 影响 | 置信度 |
|--------|------|-------------------|------|------|--------|

## 4. 语义引用

仅在需求规格包含语义关系时保留。

> 语义锚点：<变更对象、参考对象>
> 扫描结果：需要修改 N，无需修改 N，待确认 N

| 路径/符号 | 语义关系 | 处理结论 | 依据 |
|-----------|----------|----------|------|
| | | 需要修改 / 无需修改 / 待确认 | |

## 5. 同名对象消歧

仅在存在歧义时保留。

## 6. 跳过详细设计的实现要点

| 需求项 | 目标文件/符号 | 允许修改 | 禁止修改 | 验收标准 |
|--------|---------------|----------|----------|----------|

## 7. 聚合风险

| 风险 | 涉及需求项 | 证据 | 后续处理 |
|------|------------|------|----------|

## 8. 阻塞问题

| ID | 需求项 | 缺失证据或问题 | 影响 | 需要确认方 |
|----|--------|----------------|------|------------|
```

无对应内容的章节直接省略，不填充成片的 `N/A`。

## 流转门禁

只有满足以下条件才能进入 `ui-designer`、`design-writer` 或 `dev-planner`：

```text
影响面状态 = 已闭合
编码相关阻塞问题 = 0
语义引用待确认 = 0（触发语义分析时）
每个需求项已明确：进入详细设计 / 跳过详细设计
```

与本次实现无关的问题移入“非本次范围”，不能作为待定实现项继续流转。

## 自审查

```text
□ 需求规格是否已确认且无阻塞问题？
□ 端到端链路是否覆盖中间适配和通信层？
□ 新增/修改字段是否双向映射并覆盖转换、默认值和兼容？
□ 存在语义关系时，相关引用是否全部完成分类？
□ 同名对象是否按路径、符号、职责和可修改性消歧？
□ 是否只保留关键证据，没有查询流水？
□ 链路未闭合时是否停止后续流程？
```
