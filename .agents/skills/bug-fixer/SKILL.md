# Bug Fixer - Bug 修复

## 定位

`bug-fixer` 负责系统化调试和最小修复。它和 `code-tester` 形成内循环：

```text
code-tester 发现失败 → bug-fixer 修复 → code-tester 复测
```

编译失败也进入 `bug-fixer`。编译错误有明确失败命令和通过标准，适合按 Bug 修复流程处理，不让 AI 临场猜改。

---

## 铁律

**不找出根因就不修复。** 没完成证据收集和最小复现，不能进入修复阶段。禁止看到报错就猜测性修改。

---

## 触发场景

- `code-tester` 测试失败。
- 提交前编译检查失败。
- 用户描述问题：“报错”“不 work”“有 Bug”“帮我修一下”。
- code-review 指出必须修复的问题。

---

## 输入

| 输入 | 用途 |
|------|------|
| 失败证据 | 错误日志、堆栈、截图、失败命令、输入数据 |
| 最小复现 | 复现命令、测试用例或操作步骤 |
| 开发计划 | 确认关联任务、允许修改范围和状态 |
| 需求设计文档 | 确认契约设计、编码上下文和验证计划 |
| 界面设计文档 | 涉及 UI 时确认界面契约和 UI 状态 |
| 相关 diff | 确认最近变更和可能引入点 |

---

## 工作流程

### 阶段 1：收集证据

收集并记录：

```text
□ 完整错误信息、堆栈、行号、错误码
□ 失败命令或操作步骤
□ 输入数据、配置、环境信息
□ 当前分支、相关 diff、最近修改文件
□ 是否稳定复现
```

### 阶段 2：建立最小复现

将证据转成最小复现：

- 编译失败：记录最小构建命令。
- 单元失败：保留最小失败测试。
- UI 失败：记录最短操作路径和截图。
- 运行时失败：记录最小输入和触发条件。

必须确认当前代码上复现失败。

### 阶段 3：分析根因

| 类型 | 定义 | 后续 |
|------|------|------|
| 编码失误 | 需求和设计明确，实现写错 | 最小修复 |
| 编译失败 | 语法、类型、链接、依赖、构建配置错误 | 最小修复 |
| 边界遗漏 | 极端输入、异常状态、并发、资源释放未处理 | 最小修复 |
| UI 契约遗漏 | 界面契约未覆盖必要状态或交互 | 回 `ui-designer` 补充后再修 |
| 设计遗漏 | 需求设计未覆盖接口、数据、错误处理或兼容策略 | 回 `design-writer` 补充后再修 |
| 影响面遗漏 | 实际影响超出 impact-analyzer 判断 | 回 `impact-analyzer` |
| 需求遗漏 | 验收标准或业务规则缺失 | 回 `spec-analyzer` |

### 阶段 4：最小修复

修复原则：

- 只修复当前根因。
- 不扩大需求范围。
- 不做无关重构。
- 不绕过测试。
- 不屏蔽错误来制造通过。

修复后立即运行最小复现。

### 阶段 5：复测和路由

修复后：

1. 最小复现必须通过。
2. 相关验收场景必须通过。
3. 受影响范围做必要回归。
4. 回到 `code-tester` 形成复测记录。

如果修复满足任一条件，重新触发 `code-review`：

- 修改超过局部小修。
- 涉及接口、数据结构、配置、权限或 UI 契约。
- 修改了多个模块。
- code-review 原本要求修复。

## 自审查

```text
□ 是否有稳定复现？
□ 是否找出根因而不是猜测？
□ 编译失败是否记录了失败命令和错误日志？
□ 修复是否最小化？
□ 是否避免无关重构？
□ 是否回到 code-tester 复测？
□ 是否需要重新 code-review？
```
